### 최종 원칙
1. **한 계좌의 한 값에는 원본이 하나만 존재한다.**
2. `broker` 계좌는 증권사가 원본이고, `local` 계좌는 StockBook 장부가 원본이다.
3. 시세는 장부의 원본이 아니다. Quote Provider 가 제공하는 관측값이다.
4. 보유 평가액, 손익, 총자산은 원본이 아니라 파생값이다. 총자산은 **통화별로만** 계산한다.
5. 전역 `cashManual`, `totalAsset`, 다단 폴백 구조는 이관한 뒤 제거한다.

## 0. 결론

**StockBook 은 둘 다다. 다만 "누가 원본인가"는 계좌 단위로 하나만 정한다.**

| 계좌 원장 모드 (`ledgerMode`) | 원본 | StockBook 의 역할 |
|---|---|---|
| `broker` (KIS 등 API 연동 계좌) | **증권사**. 잔고·보유·체결 | 증권사 데이터를 **복사·보관(스냅샷)** 하고, 그 위에 투자 판단(일지·매수 근거)을 덧붙인다 |
| `local` (미래에셋 등 수동 계좌) | **StockBook 로컬 장부**. 거래·입출금·보정 이벤트 | **장부 그 자체**. 보유와 예수금은 장부에서 **계산**한다 |

- `ledgerMode` 는 증권사 이름이 아니라 **계좌의 속성**이다. 같은 KIS 계좌라도 API 를 연결하지 않으면 `local` 이다.
- 두 모드 모두 **1급 계좌 타입**이다.
  - 같은 계좌 인터페이스로 조회된다(§4).
  - 화면과 분석은 모드를 몰라도 동작한다.
  - 다른 점은 "숫자가 어디서 오는가"뿐이다.

## 1. 현재 코드 점검 결과

예수금 계산은 실제로 **4세대 로직이 겹쳐** 있다. 아래 1~4가 각 세대이고, 5~10은 관련 결함이다. `CLAUDE.md` §4 의 설명도 이미 실제 코드와 다르다.

| 8 | `main.js` `fetchKisBalance` (~832) | 예수금으로 `dnca_tot_amt`(예수금 총액, 당일 기준)를 사용 | 매도 직후 **D+2 정산 예정**이 반영되지 않는다. "예수금"과 "출금·주문 가능" 의미가 섞여 있다 |
| 9 | `cashflows[]` | `{date, type, amount, memo}` — **`accountId` 가 없다** | 입출금이 어느 계좌의 것인지 알 수 없다. 수동 계좌별 장부를 계산할 수 없다 (#29 스키마 v1 에도 컬럼 없음) |
| 10 | 거래 전체 | 수수료·세금 필드 없음 | 수동 계좌 예수금이 거래할 때마다 실제와 조금씩 어긋난다 (질문 3의 원인) |

## 2. 데이터별 원본 정의

**원본 · 파생 · 캐시의 정의**
- **원본**: 사용자가 바꾸거나 외부에서 받아 저장하는 값.
- **파생**: 원본에서 매번 계산하는 값. 저장하지 않는다.
- **캐시**: 계산 결과를 성능 때문에 보관하는 것. 언제든 다시 계산할 수 있다.

| 데이터 | `broker` 계좌 | `local` 계좌 | 공통 규칙 |
|---|---|---|---|
| **예수금** | 원본: 증권사 스냅샷 (`asOf` 시각 포함) | 파생: 장부 이벤트 합계 | 통화별로만 존재. 계좌 간 합산은 같은 통화끼리만 |
| **보유 수량 · 평균단가** | 원본: 증권사 스냅샷 | 파생: 거래 이벤트로 계산 | `portfolio[]` 행은 **캐시(표시용)** 로 강등 |
| **체결(거래)** | 원본: 증권사 체결 내역(가져오기) | 원본: 로컬 거래 이벤트 | 매수 근거·메모·일지 연결은 **항상 로컬 주석**. 증권사 체결에 덧붙인다 |
| **입출금** | 원본: 증권사(제공 시). 없으면 참고 기록 | 원본: 로컬 입출금 이벤트 (`accountId` 필수) | |
| **잔고 보정** | 없음. 증권사 값이 곧 정답 | 원본: **보정 이벤트** (사유·실제값·계산값 기록) | 수동 계좌 숫자를 직접 덮어쓰는 대신 이벤트로 남긴다 |
| **시세** | **원본이 아니다.** Quote Provider 가 제공하는 관측값 | 같음 | 장부에 넣지 않는다. 평가금액은 항상 파생 |
| **일지 · 매수 근거 · 목표가** | 로컬 원본 | 로컬 원본 | 계좌 모드와 무관 |
| **`cashManual` · `totalAsset`** | 폐기 대상 | 폐기 대상 (이관 후 제거, §5) | 전역 단일 값은 계좌 모델과 맞지 않는다 |

### 2-1. 핵심 규칙
1. **한 계좌의 한 값에는 원본이 하나만 있다.** 폴백 체인으로 원본을 바꿔 끼우지 않는다.
2. **`broker` 계좌에서는 로컬이 잔고 숫자를 바꾸지 않는다.**
   - 빠른 주문 같은 로컬 입력은 "주석이 달린 예정 거래"로만 남긴다.
   - 다음 동기화 때 증권사 체결과 짝짓는다.
3. **`local` 계좌의 보유와 예수금은 저장된 숫자가 아니라 계산 결과다.**
   - 실제와 다르면 사용자가 실제값을 입력한다.
   - 그러면 앱이 **보정 이벤트**(실제값 − 계산값)를 만든다.
4. **스냅샷에는 반드시 `asOf` 를 붙인다.**
   - 동기화에 실패하면 마지막 스냅샷을 "기준 시각과 함께" 보여준다.
   - **다른 원본으로 폴백하지 않는다.**
5. **총자산은 통화별로만 계산한다.** KRW 총액과 USD 총액을 각각 보여주고, 환산 합산은 하지 않는다.

## 3. 예수금 — 단일 계산 기준과 폴백 정책

### 3-1. 함수 형태
- `getCash(accountId) → { amount, currency, asOf, basis, settled, pending }`
- `getCashByCurrency(accountIds?) → { KRW: {...}, USD: {...} }`
  - 같은 통화끼리만 합산한다.
  - 전역 단일 숫자를 돌려주는 함수는 없앤다.

### 3-2. 계좌 모드별 계산

| 모드 | 계산 | `basis` 값 |
|---|---|---|
| `broker` | 마지막 성공 스냅샷의 예수금. 당일 예수금과 D+2 정산 예수금을 **둘 다 보관** | `broker_snapshot` |
| `local` | `opening + Σ입금 − Σ출금 + Σ정산금액(settlementAmount) + Σ보정` | `local_ledger` |

### 3-3. 폴백 정책 (명시적 · 단방향)

| 상황 | 처리 |
|---|---|
| `broker` 동기화 실패 | 마지막 스냅샷 + `asOf` + "갱신 실패" 상태로 표시. **로컬 계산으로 대체하지 않는다** |
| `broker` 를 한 번도 동기화하지 못함 | 값 없음 → "미동기화" 표시. 0원으로 보이지 않게 한다 |
| `local` 장부가 비어 있음 | "시작 잔고 입력" 안내. 시작 잔고는 opening 이벤트 1건으로 들어간다 |
| `broker` 의 스냅샷 이후 로컬 예정 거래가 있음 (선택 기능) | 스냅샷 값과 별도로 **"추정"** 라벨로만 보조 표시한다. 원본값을 바꾸지 않는다 |

### 3-4. 없애는 것
- `a.cash > 0` 필터
- 전역 `cashManual` 우선순위
- `totalAsset` 역산
- `calcExsugeum()` 의 전역 계산

이것들은 §5 의 이관 절차를 거쳐 제거한다.

## 4. 체결금액 · 수수료 · 세금 · 정산금액 도입

**결론: 도입이 적절하다.** 수동 계좌 예수금이 어긋나는 주 원인을 직접 해결한다.

### 4-1. 거래 필드

| 필드 | 의미 | 비고 |
|---|---|---|
| `grossAmount` | 체결금액 = 단가 × 수량 | 기존 `total` · `totalAmt` 를 이 이름 하나로 통일 |
| `fee` | 매매 수수료 | |
| `tax` | 매도 시 거래세 등 | |
| `settlementAmount` | **예수금에 실제로 반영되는 금액. 부호 포함** | 매수 = −(gross + fee), 매도 = gross − fee − tax |
| `settleDate` | 결제일 | 국내 주식 D+2 |
| `currency` | 통화 | |
| `amountSource` | 금액의 출처 | `broker`(증권사 확정) · `user`(체결 확인서 입력) · `estimated`(요율 추정) · `legacy`(구 데이터) |

### 4-2. 규칙
1. `local` 계좌 예수금은 **`settlementAmount` 만** 합산한다. 단가 × 수량을 다시 계산하지 않는다.
2. **수수료·세금을 모르면 계좌별 요율 프로필로 추정**하고 `amountSource: estimated` 로 표시한다.
   - 사용자가 체결 확인서 값을 입력하면 `user` 로 바뀐다.
   - **과거 거래는 요율이 바뀌어도 다시 계산하지 않는다.** 당시 값을 보존한다.
3. **기존 거래는 `amountSource: legacy` 로 표시한다.**
   - `settlementAmount = ±grossAmount` 로 둔다 (수수료·세금 0).
   - 누적 오차는 사용자가 실제 예수금을 한 번 맞출 때 생기는 **보정 이벤트 1건**으로 흡수한다.
4. 통화별 최소단위와 반올림(원 단위 절사·반올림 등)은 **Contract 에서 확정**한다. 이 문서에서 정하지 않는다.
5. 신용 거래(`tradeType: credit`)의 정산은 현금 거래와 다르다. 현재도 계산에서 빠져 있으며, **이번 범위 밖**으로 두고 표시만 한다.
6. `broker` 계좌는 이 필드들을 **증권사 체결·매매손익 조회에서 채운다.** KIS 가 어느 조회에서 수수료·세금을 주는지는 구현 단계에서 확인한다.

## 5. 기존 기능을 깨지 않는 이관 경로

**원칙: 이관 직후 화면에 보이는 숫자가 하나도 바뀌지 않아야 한다.** 차이는 opening·보정 이벤트로 흡수한다.

1. **#29**: 현재 값(`accounts[].cash`, `cashManual`, `cashflows`, `trades`, `portfolio`)을 **그대로** 옮긴다. 의미 변경은 없다.
2. **계좌 장부 이관 (#64, 스키마 v3)**
   1. **원장 모드 지정**
      - `broker === 'kis' && !isManual` → `ledgerMode: broker`
      - 나머지 → `ledgerMode: local`
      - 모든 계좌에 `currency: 'KRW'` 기본값
   2. **입출금의 계좌 지정**
      - `local` 계좌가 하나면 그 계좌로 지정한다.
      - 여럿이면 `accountId: null` 로 두고 "미지정 입출금" 목록에 올린다. **임의로 배분하지 않는다** (#47 미해결 종목 처리와 같은 원칙).
   3. **거래 금액 통일**
      - `total` 과 `totalAmt` 를 `grossAmount` 하나로 합친다.
      - `settlementAmount = ±grossAmount`, `amountSource: legacy`
   4. **시작 잔고 이벤트** — `local` 계좌마다 다음을 만든다.
      - 예수금: `opening = 이관 직전 화면 예수금 − 장부 계산값` → 계산값이 화면값과 정확히 같아진다.
      - 보유: 장부 계산 보유와 `portfolio[]` 행의 차이도 **opening 포지션 이벤트**로 흡수한다. 거래 없이 직접 추가한 종목이 여기에 해당한다.
   5. **`cashManual` 이관**
      - 계좌별 cash 가 비어 있고 `cashManual` 만 있으면 기본 `local` 계좌의 opening 으로 옮긴다.
      - `totalAsset` 은 과거 설정값으로만 보존하고 계산에서는 제외한다.
   6. **검증**
      - 계좌별·통화별로 이관 전후의 예수금과 보유 수량·평단이 **완전히 같아야** 한다.
      - 다르면 즉시 중단하고 롤백한다(#29 체계 재사용).
3. **`broker` 계좌 정리**는 별도 단계(#65)로 한다. 대상:
   - 유령 보유 제거
   - 체결 내역 가져오기

   사용자가 체감하는 변화가 있으므로 이관과 한 PR 에 섞지 않는다.

## 6. 멀티 증권사 구조

**결론: 적절하다.** 계좌/보유와 시세는 실패 방식, 호출 주기, 인증 방식이 모두 다르므로 분리한다.

```
                 ┌─ AccountSource 인터페이스 (계좌 = 1급 객체) ─┐
UI · 분석 ──→    │  listAccounts / getCash / getHoldings /       │
                 │  getExecutions / capabilities                 │
                 └──────┬──────────────────────┬────────────────┘
                        │                      │
          BrokerAccountAdapter          LocalLedgerSource
          (KIS · 토스 · LS · 키움)       (수동 계좌 = 장부 계산)
                        │
          main.js IPC (인증·토큰·호출 한도)

UI · 분석 ──→  Quote Provider (#48)  ──→ KIS 시세 · KRX · 네이버(EXE) · Yahoo
```

- **두 모드가 같은 인터페이스를 구현**한다.
  - 수동 계좌도 `LocalLedgerSource` 라는 "어댑터"로 조회된다.
  - 그래서 화면과 분석에서는 API 계좌와 동등한 1급 계좌다.
- 증권사 하나가 계좌와 시세를 둘 다 줄 수 있다(KIS).
  - 그래도 **등록은 따로** 한다(BrokerAccountAdapter, QuoteProvider).
  - 시세가 막혀도 잔고는 보이고, 그 반대도 마찬가지다.
- **어댑터 출력은 정규화한다.**
  - 모든 스냅샷에 `asOf`, `currency`, `assetId`(#47) 를 붙인다.
  - 증권사 원본 응답은 저장하지 않는다(디버그 로그 제외).
- **`capabilities` 로 증권사별 차이를 표현**한다.
  - 예: `executions: true/false`, `cashflows: false`, `settledCash: true`
  - UI 는 증권사 이름이 아니라 capability 로 분기한다.
- 비밀값·토큰은 지금처럼 `main.js` 에서 safeStorage 로 처리한다. 렌더러는 정규화된 결과만 받는다(`CLAUDE.md` §1-5, §1-7).

## 8. Contract 에서 확정할 계좌 · 장부 항목

`CLAUDE.md` §8 의 Contract 항목(통화, 정밀도·반올림, timestamp 등)에 아래를 더한다.

| 항목 | 이 문서의 결정 | Contract 에서 확정할 것 |
|---|---|---|
| `ledgerMode` | `broker` 또는 `local`. 계좌 속성 | 값 목록, 모드 전환 규칙 (local → broker 연결 시 장부 처리) |
| 예수금 의미 | 기본 표시는 **당일 예수금**. broker 는 D+2 정산 예수금도 보관 | 필드 이름, D+2 를 보조로 표시하는 조건 |
| 정산 필드 | `grossAmount` · `fee` · `tax` · `settlementAmount` · `settleDate` · `currency` · `amountSource` | 부호 규칙, 통화별 최소단위, 반올림 (원 단위 절사·반올림 등) |
| `amountSource` | `broker` · `user` · `estimated` · `legacy` | 값이 바뀔 수 있는 방향 (예: estimated → user 는 허용) |
| 보정 이벤트 | 실제값, 계산값, 사유를 기록 | 필드와 생성 조건 |
| opening 이벤트 | cash, position 두 종류 | 필드, 날짜 기준 |
| `asOf` | 모든 broker 스냅샷에 필수 | 시각 형식, 시간대 |
| 미동기화 · 갱신 실패 상태 | 0원이 아니라 상태로 표시 | 상태 값 목록 |
| 통화 | 다른 통화끼리 합산 금지 | `accounts.currency` 기본값 |

> `shared/docs/DATA_CONTRACT.md` 는 Contract 단계에서 만든다. `shared/` 는 해당 단계 전에는 만들지 않는다 (`AGENTS.md`). 그때까지는 이 표가 계좌·장부 계약의 입력 문서다.
