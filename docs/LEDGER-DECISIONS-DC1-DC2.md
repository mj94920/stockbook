## B. DC-1′ P″ — 미승인 검토안

출처: #89 §5. **이 절 전체는 미승인 제안이다.** Shared Contract 초판 검토 입력과 SQLite 스키마 v1(#29)을 구분한다. 필드·상태·fixture를 #29 구현 규칙이나 확정 계약으로 선반영하지 않는다.

### B-1. 제안된 표현과 항등식

- 레거시 `settleDate = null`, 결제 상태 `UNKNOWN`.
- 신규 `CALCULATED`는 결제 규칙·휴장일 출처가 정해져야 한다. 증권사 확정은 `CONFIRMED`. 경과일에 의한 추론 허용 자체도 미결이다.
- 제안 필드: `settled`, `pending`, `amount`, `unknownSettlement { net, count }`, `settledStatus`.
- 제안 항등식: `amount = settled + pending + unknownSettlement.net`.

필드명·상태명과 아래 의미는 모두 제안이며 승인된 API 또는 스키마가 아니다.

### B-2. amount 보존 주장의 한계

`amount` 불변의 전제는 **동일 거래·금액·계좌 귀속·시작 기준값·asOf에서 결제일 정보만 변경**하는 경우다. CSV 금액 정정·void 추가에는 이 불변 주장을 적용하지 않는다. “대표값은 항상 불변”이라는 주장은 유지하지 않는다.

제안상 UNKNOWN에서 결제 완료가 확인되면 unknown 순액을 settled로, 결제 전임이 확인되면 pending으로 이동한다. 위 전제에서만 amount 보존을 주장한다. 실제 이관 동치는 구현·fixture로 별도 입증해야 한다.

### B-3. 불완전성과 표시 경계

- `unknownSettlement.count > 0`이면 settled가 불완전할 수 있다. 순액이 0이어도 incomplete로 보는 제안이다. 확인·계산된 항목의 부분값을 확정 총잔고로 표시하지 않는다.
- 계좌 귀속 불명 `unattributedCash`는 계좌 밖 항목이다. 계좌는 알지만 결제일이 불명인 `unknownSettlement`와 섞지 않는다.
- settled+unknown 합성값을 당일 예수금으로 부르지 않는다. UNKNOWN=0만으로 대표 표시를 자동 전환하지 않는다. 호환 라벨·대표값 정책은 별도 결정이다.
- `opening`으로 결제일 차이를 흡수하지 않는다.

### B-4. asOf·감사·레거시 검증 제안

- asOf에는 현재 정보로 과거를 재계산하는 방식과 당시 알던 정보까지 재현하는 방식이 있다. 전자를 우선한다는 방향 및 append-only 감사 기록은 시스템룸 제안이며 미승인이다. 감사 스키마도 미결이다.
- 레거시 `calcExsugeum`은 `tradeType !== 'credit'`만 합산한다. 기존 동작 보존 fixture와 미래 신용 정책 fixture를 구분한다.
- UNKNOWN 지정만으로 숫자 보존을 입증할 수 없다. #63 이후의 `accounts.cash`, `cashManual`, `totalAsset` 역산, `calcExsugeum` 경로별 동치 검증이 필요하다. 귀속 불명 현금의 임의 배분을 금지한다.
- fixture 후보: 결제 완료/전 확인, 순액 0·건수 양수, 귀속 불명과 결제 미확인 공존, 경로별 레거시 비교, 신용 제외, 휴장일 미정, 과거 asOf, 금액 정정·void 별도 사례.
