# StockBook 2차 구조 개편 — 작업 지시서

- 에픽: #46 · 하위: #47 #48 #49 #50 #51 #52 · 선행: #29
- 확정: 2026-10-10. 순서는 `CLAUDE.md` §8-2 게이트와 `docs/SQLITE-STORAGE-DESIGN.md`(#29 설계, 승인)를 따른다.
- 이 문서와 이슈 본문이 다르면 **이 문서를 먼저 고치고** 이슈를 맞춘다.

---

## 1. 목적

UI 2차 개편(#36–#40)과 별개로, 앞으로 만들 기능을 안정적으로 올릴 데이터·코드 구조를 정리한다.
앞으로 만들 기능은 종목 타임라인, 매수 이유 분석, 규칙 엔진, AI 분석이다.

새 기능을 만드는 작업이 아니다. **이미 있는 데이터를 '종목' 하나를 중심으로 연결하는 기반 작업이다.**
연결 대상은 거래, 투자일지, 포트폴리오, 관심종목, 메모다.

1. **UI 2차(#36–#40)를 먼저 끝낸다.** 둘 다 `index.html` 을 직접 고치므로 구조 개편과 동시에 진행하지 않는다.
2. 그다음 **#29 SQLite → #47 → Contract → #48 → #49 → #50** 순서로 진행한다.
3. **#51 · #52 는 #47 완료 후 바로 착수할 수 있다.** #49 · #50 을 기다리지 않는다.
4. **작업 큐 시작 조건**
   - UI 2차 대기열이 끝나면 **#29 부터** `queue` 라벨을 붙인다.
   - 그 전에는 이 묶음에 `queue` 를 붙이지 않는다.
   - #47 의 마이그레이션과 검증이 끝나기 전에는 #51 · #52 본 구현을 시작하지 않는다.

## 4. #47 — 종목 중심 통합 객체 (Stock identity)

**현재 문제**
- 거래(`trades`)와 투자일지(`journals`)는 종목을 **종목명 문자열**로만 가리킨다.
- 포트폴리오와 관심종목 일부에는 종목코드가 없다.
- 이 상태로는 같은 종목의 다음 항목을 안정적으로 묶을 수 없다.
  - 거래, 일지, 잔고, 관심종목, 목표가
  - 앞으로 만들 타임라인과 매수 이유별 성과

**식별자 규칙** (`CLAUDE.md` §8-3-3, #29 설계 §3-4)

| 구분 | 무엇 | 용도 |
|---|---|---|
| `assetId` | StockBook 이 발급하는 **불변 opaque ID** (UUID 계열) | **모든 내부 관계의 유일한 키**: 보유 · 거래 · 일지 · 관심 · 메모 |
| `market + stockCode` | 시장의 외부 식별자. `assets` 에서 `UNIQUE(market, stock_code)` | 종목을 **찾는 기준**과 시세 매핑. 관계 키로 쓰지 않는다 |
| `name` | 표시값 | 식별에 쓰지 않는다 |

- `assetId` 는 `market + stockCode` 에서 계산하지 않는다(해시 금지).
  - 시장 이전이나 코드 변경이 있어도 `assetId` 는 그대로 둔다. 예: 코스닥 → 코스피 이전상장.
  - 바뀐 값은 `assets` 행의 속성만 고친다.
- ETF 는 같은 Asset 아래 `asset_type = 'etf'` 로 구분한다.

**마이그레이션 원칙**
- 단독 작업이다. 다른 기능 구현과 섞지 않는다.
- **#29 의 백업·검증·롤백 체계를 재사용한다.** 기존 JSON 위에 #47 전용 마이그레이션을 따로 만들지 않는다.
- 코드가 없는 기록은 종목명과 기존 시장 정보로 매핑한다.
  - **자동 매핑이 불확실하면 임의로 연결하지 않는다.** `asset_id = NULL` 로 남기고 실패 목록에 올린다.
  - 사용자가 데이터 관리 화면에서 직접 연결한다.
- 마이그레이션은 여러 번 돌려도 결과가 같아야 한다(멱등). 이미 발급된 `(market, stockCode) ↔ assetId` 매핑은 보존한다.

**필수 절차**
1. 기존 데이터 백업
2. 마이그레이션 실행
3. 연결 검증: 테이블별 연결 수와 미연결 수
4. 실패(미연결) 목록 확인
5. 롤백 가능 여부 확인
6. **이전 전후로 기록 수가 예상과 다르면 즉시 중단하고 롤백한다.**

## 5. #51 — 종목 타임라인 MVP (#47 이후 조기 구현)

- **기다리지 않는 것**: 시계열 가격 DB, 규칙 엔진, AI 분석. 사용자에게 보이는 기능으로 먼저 낸다.
- **1차 대상** (기존 데이터를 시간순으로 통합)
  - 매수, 추가매수, 매도
  - 투자일지
  - 목표가 변경, 손절가 변경
  - 관심종목 등록
- **목표가·손절가 이력**: 지금은 값을 덮어써서 이력이 남지 않는다. 이번에 이력 저장을 시작하며, 과거 변경은 복원하지 않는다.
- **구조**: `Stock(assetId) → Events[]`
  - 이벤트 공통 형식: `{ assetId, at, kind, title, detail, ref }`
  - 나중에 같은 형식으로 붙일 것: 공시, 실적 발표, 가격 이벤트, Rule Signal, AI 판단 변경
- **미래 기능을 억지로 미리 구현하지 않는다.**

## 6. #52 — 매수 이유 표준화 (#47 이후)

1. **첫 단계: 이름 통일**
   - 지금은 같은 데이터가 두 이름으로 있다: 거래 `buyReason`, 투자일지 `buyReasons`
   - 이를 복수 선택형 표준 구조 하나로 합친다: `buyReasons: []`
   - 이 단계는 #29 의 마이그레이션 체계 위에서 진행한다.
2. **표준 이유 목록**: 실적개선 · 기술적반등 · 저평가 · 수급 · 이벤트 · 장기성장 + 사용자 정의
3. **연결**: 매수 이유 → 해당 거래 → 이후 성과(실현 수익률, 보유일수)
   - 계산은 앱의 평균단가 방식과 일치시킨다.
4. **표본이 적으면 수치를 의미 있게 보이지 않게 한다.**
   - 5건 미만은 수치 대신 **"표본 부족"** 으로 표시한다.
5. **나중에 붙일 것**
   - "원칙 위반 거래" 플래그는 #50(Signal)이 생긴 뒤에 붙인다.
   - 보유 중 최대 이익/손실은 #49 이후에 붙인다.

## 8. #48 — Provider Adapter, CORS 프록시 제거

- 현재 일부 외부 데이터 호출이 제3자 프록시 `corsproxy.io` 에 의존한다.
  - 이 서비스가 멈추면 해당 기능도 함께 실패한다.
  - **이 의존성을 제거한다.**
- **목표: UI 는 외부 공급자를 직접 호출하지 않는다.**

```
UI
 ↓
Data Service        ← 표준 데이터(Quote · Candle · Disclosure …)만 주고받음
 ↓
Provider Adapter    ← 우선순위 · 실패 시 폴백 · 오류 기록
 ├─ KIS / OpenDART / KRX   (공식, 우선)
 └─ 네이버 / Yahoo / Investing   (비공식, 보조 · 네이버는 EXE 전용)
```

- 외부 공급처가 바뀌어도 UI 코드를 고치지 않는 구조를 만든다.
- 진행 방식: 계층을 도입하고 **시세(Quote) 하나를 먼저** 옮긴다. 나머지는 후속 PR.

## 9. #49 — 시계열 데이터 계층 (#29 · #48 이후)

- #47 의 `assetId` 를 키로 저장한다.
- **초기 범위**
  - 일별 가격(시가·고가·저가·종가)
  - 거래량, 거래대금
  - 이동평균 계산에 필요한 기간
- 다음 데이터는 후속으로 확장한다: 수급, 밸류에이션, 분기 재무
- **수집 범위**: 보유 + 관심 종목부터. 처음 열 때 과거치를 백필하고, 이후 매일 증분으로 쌓는다.
- 저장 형태는 규칙 엔진(#50)이 그대로 읽을 수 있게 만든다.
- 조회 헬퍼 예: `series` · `avg(n)` · `streak` · `pctOfAvg(n)`

## 10. #50 — Rules Engine / Signal (#49 이후)

- 투자원칙을 UI 문장으로 처리하지 않는다. **구조화된 Signal 객체**를 반환한다.

```
Signal {
  stockId      // = assetId
  ruleId
  type         // 예: drop · golden_cross · volume_surge · stop_hit · target_hit · disclosure
  severity     // info · notice · warn · danger
  value        // 판정에 쓴 수치
  reason       // 사람이 읽는 근거 문장
  generatedAt
}
```

- 평가기는 **순수 함수**로 만든다. DOM 없이 단위 테스트한다.
- 규칙은 코드 곳곳에 두지 않고 **데이터(규칙 정의)** 로 관리한다.
- 같은 Signal 을 여러 곳에서 공유한다: 전종목 창, 종목 상세, 잔고, 타임라인, AI 분석
- **AI 의 역할**: 원시 데이터를 다시 계산하지 않는다. 규칙 엔진의 결과와 근거를 해석하는 상위 계층이다.

## 11. 코드 분리 원칙

- `index.html` 은 이미 13,000줄이 넘는다. **새 도메인 로직은 `index.html` 안에 작성하지 않는다.**
- 이번 구조부터 별도 파일을 쓴다. 디렉터리 이름은 첫 PR 에서 확정한다. 예:

```
src/
  stocks/      # Asset · assetId 조회
  providers/   # Provider Adapter · Data Service
  timeline/
  rules/
  portfolio/
  journal/
```

- 새 파일을 만들면 함께 할 일:
  - Electron `package.json` `build.files` 에 포함
  - Pages 에서도 로드되는지 확인
  - 정적 검사(`scripts/check-syntax.mjs`) 대상에 추가
    - 검사 변경이므로 PR 에 `tests-approved` 가 필요하다 (`CLAUDE.md` 규칙 9)
- 이번 작업을 거대한 `index.html` 을 단계적으로 분리하는 출발점으로 삼는다.

## 12. 기존 기능 보존

**깨뜨리지 않아야 할 기능**
- 전종목, 관심종목
- 포트폴리오/잔고, 거래 등록, 평균단가 계산
- 투자일지, 목표가/손절가
- 실시간 가격 호출, 기존 API 연결

**기존 데이터를 가진 사용자는 업데이트 후에도 그대로 써야 한다.**
마이그레이션이 끝나지 못하면 기존 저장소로 동작한다.
