# StockBook 2.0 업종·테마 시스템 — 최소 구조 설계안 (제안 · 구현 없음)

상태: **설계 제안. 저장소에 반영하지 않음. 구현하지 않음.**
게이트 순서 불변: #29 → #47 → Contract Gate → #48 → #49 → #50 → Android Gate.
전제: **분류체계(taxonomy)와 공급자는 확정되지 않았다.** 이 문서의 키 이름·분류·기업 소속은 구조를 설명하기 위한 예시이며, 어떤 공급자나 분류체계를 가정하지 않는다.
짝 파일: `semiconductor-example.json` — 반도체 예시 데이터(구조 검증용, **실제 분류·사업 설명 아님**).

---

## 0. 요구사항 (사용자 관점, 설계의 입력)

1. 업종 아이콘은 장식이 아니라 **업종별 기업 탐색의 진입점**이다.
   `업종 아이콘 → 업종 화면 → 그 업종의 산업/사업 분야와 기업 → 기업 선택 → 종목 상세`
2. 기업 목록에는 필요에 따라 **영위 사업 정보**와 **StockBook 분석 정보**를 함께 표시할 수 있어야 한다.
3. 거대한 대·중·소분류 taxonomy 를 **지금 확정하지 않는다.** "산업 기준으로 관련 기업을 탐색할 수 있다"가 핵심.
4. **업종(산업 기반)과 테마(횡단 분류)는 별개**다. 아이콘 그래픽은 UI 자산이며 시스템은 **식별자만** 제공한다.

## 1. 결론 요약

| 질문 | 제안 |
|---|---|
| 최소 모델 | **산업 노드(트리) · 종목 참조 · 산업 링크(N:M) · 테마 · 테마 소속** 5개 + 데이터셋 메타 |
| 기업 ↔ 사업 | 기업(종목)이 **여러 산업 노드에 링크**되고, 링크가 "이 기업의 이 분야 사업" 설명을 가진다 |
| 다사업 기업 | 링크 여러 개 + **PRIMARY 는 종목당 정확히 1개**, 나머지 SECONDARY |
| 아이콘 연결 | **`industryKey`**(불변 슬러그). UI 가 `industryKey → 아이콘`을 자체 매핑 |
| 업종 vs 테마 | 업종은 **트리·사실 기반·종목당 최소 1개·안정적**, 테마는 **평면·큐레이션·0개 가능·수명 있음** |
| 공급원 분리 | **3층: 공급원 원본 → 매핑 → StockBook 산업 트리.** Contract 는 3층(StockBook 소유)만 규정 |
| 공유 Contract 범위 | 스키마 5종 + 식별자 규칙 + 작은 fixture. **수집·매핑·큐레이션 코드와 아이콘은 공유 안 함** |
| 숫자 | 트리 깊이·분류 수를 고정하지 않는다(깊이 무제한 `parentKey`, 예시는 2단) |

## 2. 최소 데이터 모델

### 2-1. IndustryNode — 산업/사업 분야 트리
```
IndustryNode {
  industryKey   // 불변 슬러그. 아이콘 연결·참조의 유일한 키
  parentKey     // null 이면 최상위. 깊이 제한 없음
  entry         // true 면 홈/탐색의 "업종 아이콘" 진입점 후보
  name {ko}     // 표시명(변경 가능). 키와 분리
  status        // ACTIVE | DEPRECATED
  replacedBy    // DEPRECATED 일 때 대체 키(선택)
  order         // 표시 순서
}
```
- "업종"과 "산업/사업 분야"를 **다른 타입으로 만들지 않는다.** 같은 노드 타입이고, 아이콘으로 노출되는 최상위(`entry:true`)가 "업종", 그 아래가 "산업/사업 분야"다. 단계 수가 확정되지 않아도 구조는 바뀌지 않는다.
- **키는 계층을 인코딩하지 않는다**(예: `semiconductor.memory` 금지). 노드를 다른 부모로 옮겨도 키가 유지되어야 하기 때문이다. 부모 관계는 `parentKey` 로만 표현한다.

### 2-2. InstrumentRef · InstrumentProfile — 종목 참조와 영위 사업 설명
```
InstrumentRef { market, stockCode }         // 외부 식별자
InstrumentProfile {
  ref, name{ko},
  businessSummary {ko}                       // 짧은 영위 사업 설명
  sourceId, asOf                             // 출처·기준일
}
```
- **데이터셋의 종목은 `assetId` 가 아니라 `(market, stockCode)` 로 참조한다.** 이유는 §6 의 중요 발견 참조.

### 2-3. IndustryLink — 기업 ↔ 산업 (N:M)
```
IndustryLink {
  ref,                       // 종목
  industryKey,               // 산업 노드
  role,                      // PRIMARY | SECONDARY
  weight?,                   // 선택(매출 비중 등). 없어도 되며 필수로 요구하지 않는다
  businessNote? {ko},        // "이 기업의 이 분야 사업"
  basis { sourceId, ... }    // 근거 출처
}
```
- 기업이 여러 사업을 영위하면 **링크를 여러 개** 둔다. 기업은 자신이 속한 **모든 노드의 목록에 나타난다.**
- **불변식:** 종목당 PRIMARY 는 **정확히 1개**. PRIMARY 는 "대표 소속"(기본 그룹핑·업종 통계의 중복 집계 방지)이며 판단은 큐레이션 결정이다.
- `weight` 는 데이터 확보가 어려울 수 있어 **선택**으로 둔다(없으면 순서·PRIMARY 로만 구분).

### 2-4. Theme · ThemeMember — 테마
```
Theme {
  themeKey, name{ko}, description{ko}?,
  status, validFrom, validTo?          // 수명
}
ThemeMember {
  themeKey, ref,
  relevance,                           // CORE | RELATED
  rationaleCode?,                      // 편입 근거 코드(자연어 문장은 계약에 두지 않음)
  basis { sourceId, asOf }
}
```

### 2-5. DatasetMeta
`datasetVersion`, `generatedAt`, `sources[]`(sourceId·kind·asOf). 클라이언트가 어느 시점의 분류를 보고 있는지 알기 위한 최소 메타(기준 시각 표시 원칙과 같다).

## 3. 업종과 테마의 구조적 차이

| | 업종(산업 기반) | 테마(횡단 분류) |
|---|---|---|
| 정의 | 기업이 **실제로 영위하는 사업** | 투자 관점의 **서사·주제**(AI·로봇·원전 등) |
| 구조 | **트리**(parentKey) | **평면**(필요 시 군집은 별도 결정) |
| 기업당 소속 | **최소 1개**(PRIMARY 1), 여러 개 가능 | **0개 가능**, 여러 개 가능 |
| 근거 성격 | 비교적 **사실 기반**(사업보고서·표준분류로 검증 가능) | **큐레이션·의견**이 섞임, 근거 코드로 설명 |
| 변동성 | 느림 | **빠름**(생성·소멸, `validFrom/To`) |
| 소속 강도 | 역할(PRIMARY/SECONDARY), 선택적 비중 | `relevance` CORE/RELATED |
| UI 진입 | 아이콘 → 업종 화면 | 별도 진입(테마 카드). **아이콘 체계와 섞지 않음** |
| 테마가 업종을 참조? | — | 필요 시 `includesIndustryKeys` 로 업종을 묶을 수 있으나 **지금은 결정하지 않음**(열린 질문) |

**섞지 않는 이유:** 테마를 업종 트리에 넣으면 한 기업이 여러 가지에 걸치는 횡단 구조가 트리를 깨고, 수명이 짧은 항목이 안정 키를 오염시킨다.

## 4. 영위 사업을 가진 기업 목록을 UI 가 만드는 방법 (탐색 증명)

예시 `semiconductor-example.json` 기준(실제 분류 아님).

| 단계 | 동작 | 결과(예시 데이터) |
|---|---|---|
| 1 | 아이콘 `semiconductor` 선택 | `industryKey = semiconductor` (`entry:true` 노드) |
| 2 | 하위 분야 조회: `parentKey == semiconductor` | `memory-chip`, `foundry`, `semi-equipment`, `semi-materials` |
| 3 | 소속 기업: 서브트리의 `IndustryLink` 를 분야별로 묶음 | `memory-chip`: 삼성전자(PRIMARY)·SK하이닉스(PRIMARY), `foundry`: 삼성전자(SECONDARY), `semi-equipment`: 한미반도체, `semi-materials`: 솔브레인 |
| 4 | 기업 행 구성 | `InstrumentProfile.businessSummary` + 링크의 `businessNote`("이 분야 사업") + **로컬 분석 요약**(`AssetAnalysis`, #50 — 계약의 시장 데이터에서 클라이언트가 계산) |
| 5 | 기업 선택 | `(market, stockCode)` → 클라이언트의 `assets` 매핑으로 `assetId` → **종목 상세** |

검증(스크립트로 확인함): 위 JSON 에서 (a) 모든 링크가 존재하는 노드·종목을 가리킴 (b) 종목당 PRIMARY 정확히 1개 (c) `semiconductor` 서브트리 조회 시 4개 종목이 나오고 **삼성전자가 메모리·파운드리 두 분야에 모두 나타남**. 삼성전자는 `consumer-electronics` 에도 링크되어 있어 **반도체 화면과 가전·모바일 화면 양쪽에서 탐색**된다(다사업 처리).
테마 예시: `ai` 테마가 반도체 기업(SK하이닉스·한미반도체)과 비반도체 기업(NAVER)을 **가로질러** 묶는다 — 업종 트리로는 표현할 수 없는 구조.

## 5. 공급원 확보와 3층 분리

### 5-1. 공급원 후보 (전부 **미검증 후보**. 선택·확정 아님)

| 후보 | 알려진 성격 | 검증해야 할 것 |
|---|---|---|
| 거래소 업종 분류 | 상장 종목별 업종이 있음 | **세분성**(반도체 → 메모리/장비 수준으로 나뉘는지)·이용 조건 |
| 한국표준산업분류(KSIC) | 사업 기준 국가 표준 코드 | 개정 간 코드가 **1:1 이 아님**(10차→11차), 상장사 코드 연결 방법, **이용허락 조건이 자료마다 달라 보임**(출처 표시/상업적 이용 제한 표기 혼재) |
| 공시 시스템(DART) | 사업보고서의 사업 내용·주요 제품 등 **공식 텍스트** | 어떤 API 가 구조화된 사업 정보를 주는지(검색으로는 엔드포인트 목록을 확인하지 못함), 이용 약관, 텍스트를 요약해 쓸 때의 책임 |
| 증권사 API 종목 마스터(KIS 등) | 업종 코드 제공 가능성 | 필드 구성(검색으로 확인하지 못함), 약관, 키 필요 여부 |
| 포털(네이버 등) 업종·테마 | PC 가 이미 **비공식 JSON** 을 사용 중 | **약관·안정성(비공식 엔드포인트)**, 분류가 포털 내부 정의라 변경 통지가 없음, 재배포 가능성 |
| 상용 분류(WICS·GICS 등) | 잘 정리된 체계 | **라이선스 비용·재배포 제한** |
| **StockBook 자체 큐레이션** | 완전한 통제 | 인력·검수 비용, 범위 폭발 |

현실적 관찰: "반도체 → 메모리/장비/소재" 수준의 사업 분야는 **어느 공급원도 그대로 주지 않을 가능성이 높고**, 결국 소스 코드를 StockBook 노드로 **매핑**하고 일부는 **큐레이션**해야 한다. 이는 가정이 아니라 위험이며 §8 의 첫 검증 작업 대상이다.

### 5-2. 3층 분리 (권장)

```
[1층] 공급원 원본            [2층] 매핑                 [3층] StockBook 산업 트리 (Contract)
  SourceClassification  ──▶  SourceMap                ──▶  IndustryNode / IndustryLink
  (공급원이 준 그대로,         (공급원 코드 →              (StockBook 소유 · 안정 키 ·
   코드·이름·기준일)            industryKey, 매핑 버전)       공개 데이터셋의 단위)
```

- **1층은 수정하지 않는다.** 공급원이 준 값을 기준일과 함께 보존한다(감사·재처리용).
- **2층이 공급자 교체를 흡수한다.** 공급자가 바뀌거나 분류가 개정돼도 StockBook 키는 유지되고 매핑만 바뀐다. 개정 매핑이 1:1 이 아닌 문제(KSIC)도 여기서 다룬다.
- **3층만 PC·Android 가 공유한다.** Android 는 공급원 원본·코드를 알 필요가 없다. 분류가 공급원에 종속되면 공급원 약관·재배포 제한이 앱에 그대로 전염되므로 분리가 필요하다.
- **매핑 불가 종목:** 3층에 링크가 없는 종목은 "미분류"로 표시한다(데이터 충분성의 업종 버전 — 조용히 누락하지 않음).
- **분리의 한계:** 3층에도 `basis.sourceId`·`asOf` 는 둔다(출처 표기 의무가 있을 수 있음). 원본 코드는 `sourceRefs` 로 **선택적**으로 남길 수 있다(결정 필요).

### 5-3. 생산·전달 경로 (제안)
- 3층 데이터셋은 `data` 브랜치 일일 JSON(#31)과 **같은 방식으로 배치 생성**해 Android 가 읽는다(직접 호출 금지 원칙 유지). 규모(상장 종목 수천 개, 링크 수천~수만 행)는 파일 몇 개로 충분하다고 보지만 **측정 전 추정**이다.
- 큐레이션 입력(2층·3층)은 **저장소에서 PR 로 변경·검수**할 수 있는 형태를 우선 고려한다(변경 이력·검토).
- PC 는 같은 데이터셋을 쓴다. 데이터셋 자체는 `market.db`/`stockbook.db` 중 어디에 캐시할지는 구현 단계 결정.

## 6. 중요 발견 — assetId 의 범위 (Contract Gate 에서 반드시 결정)

#47 은 `assetId` 를 **StockBook 이 발급하는 불변 opaque ID 이며 `market + stockCode` 에서 계산하지 않는다**고 정한다(이슈 본문 확인). 이 때문에:

1. **공개 데이터셋(업종·테마)은 `assetId` 를 키로 쓸 수 없다.** 설치마다 발급되는 값이라 데이터셋이 가리킬 수 없다 → 데이터셋은 `(market, stockCode)` 로 참조하고, **클라이언트가 자기 `assets` 매핑으로 `assetId` 에 연결**한다(위 §2-2·§4 가 이 방식).
2. **PC ↔ Android Export/Import 에서도 같은 문제**: 두 기기가 같은 종목에 서로 다른 `assetId` 를 발급하면 일지·관심종목 병합이 깨진다. D-S1(PC 원본)이므로 **PC 가 발급한 `assetId` 를 패키지에 실어 Android 가 채택**하는 규칙이 필요하다. Android 단독 신규 종목(관심 추가)은 발급 주체를 정해야 한다(Android 발급 후 Import 시 PC 가 수용?).
3. 대안 검토 대상: 발급 주체를 **하나의 레지스트리(공개 데이터셋)** 로 두는 방식. 이것은 #47 의 "계산하지 않는다" 원칙과 충돌하지 않는다(공개 레지스트리가 *발급*하는 것이므로).

→ 이는 업종·테마 이전에 **Contract Gate 의 필수 결정**이다. #47 구현 전에 정해야 하며 **이 문서는 결정하지 않는다.**

## 7. PC 와 Android 가 공유할 Contract 범위

| 구분 | 공유한다(`shared/`) | 공유하지 않는다 |
|---|---|---|
| 스키마 | IndustryNode · InstrumentRef/Profile · IndustryLink · Theme · ThemeMember · DatasetMeta | 공급원별 원본 스키마(1층) |
| 규칙 문서 | `industryKey` 불변·키는 계층 비인코딩, PRIMARY 종목당 1개, DEPRECATED/`replacedBy` 처리, 미분류 표시, 아이콘 키 폴백 | 매핑·큐레이션 절차(저장소 내 도구) |
| fixture | 작은 데이터셋 + "서브트리 탐색 결과" 정답(§4 의 단계 3) | 수집·크롤러·어댑터 코드(#48) |
| 식별자 | `industryKey`, `themeKey`, `InstrumentRef` | 아이콘 그래픽, 아이콘 파일명 규칙 |
| 아이콘 연결 | **계약은 `industryKey` 만 규정.** `industryKey → 아이콘` 매핑은 각 UI 소유 | 아이콘 자산 |
| 폴백 | 알 수 없는 `industryKey`(데이터셋이 앱보다 새 경우)는 **기본 아이콘으로 표시하고 기능은 유지** — 계약 규칙으로 명시 | |

fixture 가 검증할 것(JS·Kotlin 동일 결과): 서브트리 조회, 다사업 기업의 다중 노출, PRIMARY 불변식 위반 시 거부, DEPRECATED 키 리다이렉트, 미분류 종목 처리.
(분석 정보는 업종 계약이 아니라 #50 의 `AssetAnalysis` — 업종 화면은 두 계약을 조합할 뿐이다.)

## 8. 열린 질문 (결정 필요 · 이 문서는 정하지 않음)

| # | 질문 |
|---|---|
| I-1 | **assetId 발급 주체**(§6) — Contract Gate 필수 |
| I-2 | **공급원 후보 검증**: 세분성·약관·재배포·안정성. 어느 공급원으로도 "반도체 하위 분야"가 안 나오면 큐레이션 범위를 어디까지 둘지 |
| I-3 | **초기 범위**: 아이콘 진입 업종 수(제안: 작게 시작, 예 10~20), 미분류 허용 비율, 커버리지 기준 |
| I-4 | **기업 vs 종목**: 업종은 기업 단위인데 UI 는 종목을 선택한다. 보통주/우선주, ETF·SPAC·지주회사를 업종 소속에 넣을지(제안: 기본은 보통주만, ETF 제외, 확인 필요) |
| I-5 | 영위 사업 설명의 출처와 방식: 공시 원문 요약인지 큐레이션 문장인지, 언어, 길이, **자동 요약이면 오류 책임** |
| I-6 | 업종 화면의 기업 목록이 분석 요약을 함께 보이려면 **다수 종목의 일봉이 필요**하다. 로컬 계산(대량 데이터 필요) vs 일일 사전계산 요약 배포(같은 fixture 로 동일성 보장 필요) — #48/#49 와 연결 |
| I-7 | 테마가 업종을 포함하는 규칙(`includesIndustryKeys`)을 둘지, 테마 편입 근거·갱신 책임 |
| I-8 | 분류의 **시점**: 일지에 자동 첨부되는 스냅샷에 소속 업종을 넣을지(분류가 바뀌어도 당시 기록 유지) |
| I-9 | 해외 종목의 업종 체계(국내와 같은 트리를 쓰는지, 시장별 분리인지) — O-3 과 연결 |
| I-10 | 이 작업의 이슈 위치: 현재 #48~#52 에 **업종·테마가 없다**. #48 확장인지, Contract Gate 이후 별도 이슈인지 |

## 9. 게이트와의 관계

- **지금 하지 않는 것:** 구현, 공급원 선택, 분류체계 확정, `shared/` 생성, 이슈 상태 변경.
- **Contract Gate 입력:** I-1(assetId), 데이터셋 참조 규칙(`InstrumentRef`), 3계층 경계, `industryKey` 불변 규칙.
- **#48 과 연결:** 공급원 어댑터·배치 생성, I-2·I-5·I-6.
- **다음 회의 순서 제안:** (1) I-1 assetId 발급 주체 (2) I-2 공급원 후보 검증 계획 (3) I-3 초기 범위 (4) 나머지.
